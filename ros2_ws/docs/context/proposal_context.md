## 1. Project Title and Research Direction

**Title:** "Visuomotor Context-Based Meta-Reinforcement Learning with Virtual-Force Safety for Adaptable Peg-in-Hole Assembly in Smart Manufacturing"

**Direction:** Adaptive industrial assembly in collaborative smart manufacturing cells. Reliable peg-in-hole insertion under realistic part/process variability, combining learning-based control with classical geometric planning for the contact-dominant regime.

---

## 2. Main Research Problem

**Central research question (Section 4):**

> How can a collaborative robot learn a safe, robust, and rapidly adaptable peg-in-hole insertion skill from RGB-D and force/proprioceptive feedback, such that performance generalizes across multiple part variants with minimal manual re-tuning?

Three sub-questions:
1. How should RGB-D + force/proprioceptive signals be encoded for closed-loop insertion under partial observability?
2. Can context-based meta-RL infer latent context from short interaction histories to improve adaptation across variants?
3. What is the measurable safety/robustness impact of admittance/virtual-force mediation (contact) + runtime safety filter (pre-contact)?

---

## 3. Scientific Motivation

- Smart manufacturing needs assembly skills reliable under product changes, tolerance variation, and uncertain contact.
- Purely geometric planning is insufficient once contact begins (jamming, wedging, edge contact).
- No existing framework jointly addresses: multi-modal contact-state disambiguation, fast context-based online adaptation across geometry/tolerance regimes, *and* safety-constrained sim-to-real deployment.
- The literature lacks a unified, reproducible pipeline combining RGB-D visuomotor perception + context-based meta-RL + admittance/virtual-force contact mediator + runtime safety filter + simulation-backed sim-to-real workflow.

---

## 4. Target Robotic Task

Peg-in-hole assembly: single peg insertion into a fixed hole fixture under tolerance/geometry variation. Classical assembly benchmark for contact-rich industrial skill.

**Assumptions:**
- Single peg, single hole per trial
- Part variants differ in geometry and tolerance
- Nominal approach trajectory generated by classical geometric planning (IK, frame calibration, pose estimation)
- Learning-based controller operates during contact onset, alignment correction, insertion, and recovery

## 9. Learning/Control Method

### 9.1 Context-Based Meta-RL

| Component | Detail |
|-----------|--------|
| **Algorithm** | Context-conditioned Soft Actor-Critic (SAC) (Haarnoja et al., 2018; Rakelly et al., 2019) |
| **Context buffer** | Short-horizon, K = 25–75 steps at 50 Hz (0.5–1.5 s window) |
| **Buffer contents** | Encoded visual features, wrench signals, proprioception, previous actions, event flags |
| **Context encoder** | Deterministic sequence encoder (GRU or compact Transformer). PEARL-style probabilistic context informs design conceptually but deterministic vs. variational is an implementation decision |
| **Latent variable** | z — represents task variant + current contact situation |
| **Ablations** | A1: no-context / fixed-context / history-based context variants |
| **Training** | Simulation-based, off-policy, large-scale rollouts under controlled variability |
| **Policy output** | Continuous motion or force-guidance commands appropriate for current insertion phase |

### 9.2 Multi-Modal Observations

| Modality | Features extracted |
|----------|-------------------|
| RGB-D | Relative pose, local geometry cues, approach alignment |
| Force/torque | Contact onset, resistance, motion state |
| Proprioception | Joint positions/velocities |

The three modalities are fused into a unified state representation. The context module operates over the fused representation history.

### 9.3 Safety Layer (Dual-Layer Architecture)

| Phase | Mechanism | Role |
|-------|-----------|------|
| **Contact phase** | Admittance-based virtual-force layer | Modulates compliance, bounds interaction forces, shapes motion, preserves task progress, reduces unsafe contact events |
| **Pre-contact / free motion** | Runtime safety filter | Supervises velocity limits, workspace boundaries, approach-region constraints. May project, override, or stop unsafe commands |

The two layers are independent: the admittance layer governs contact behavior; the safety filter governs pre-approach constraint enforcement. Ablation A3 separates removal of each layer.

### 9.4 Virtual / Admittance Force Concept

- The admittance layer is the primary mechanism for safe contact-phase behavior.
- Draws conceptually on "virtual guiding force" (Zang et al., 2025) and classic compliant control (Raibert & Craig, 1981; Whitney, 1982).
- Aligned with collaborative robot safety standards (ISO/TS 15066, 2016).

**Missing / needs confirmation:**
- Admittance controller parameters (stiffness, damping, force limits) not specified.
- How virtual force is computed from policy output not detailed.
- Safety filter implementation approach (CBF, projection, override) not specified — only described at the methodological level.
- Safety filter constraints (velocity bounds, workspace geometry) not enumerated.

## 10. Evaluation Metrics

### Primary Metrics

| Metric | Definition | Purpose |
|--------|------------|---------|
| **Safe Success** | Task completion with zero hard constraint violations | Primary task + safety combined metric |
| **Adaptation speed** | Episodes to reach target success on unseen variants | Measures meta-learning efficacy |
| **Hard constraint violations per episode** | Count of safety-limit breaches | Safety filter effectiveness |
| **Safety-filter interventions per episode** | Count of runtime filter activations | Quantifies how often the layer must intervene |

### Secondary Metrics

| Metric | Notes |
|--------|-------|
| Nominal success rate | Raw success (ignoring safety) |
| Insertion time / cycle time | Duration from approach start to full insertion |
| Peak contact force/wrench | Maximum measured interaction force |
| Cumulative wrench | Integrated force over the trial |
| Recovery frequency | How often the system recovers from misalignment |

### Hypotheses Being Tested

- H1.1: Multi-modal > single-/dual-modality in Safe Success + peak wrench
- H1.2: Explicit contact-state disambiguation reduces jamming/wedging
- H2.1: Context-based meta-RL reduces adaptation episodes vs. single-task SAC
- H2.2: Context inference improves cross-variant robustness vs. category-level meta-policy
- H3.1: Admittance layer reduces peak wrench + violation frequency
- H3.2: Runtime safety filter prevents pre-contact violations

## 11. Constraints Guiding ROS/Gazebo Implementation

These constraints must be respected when implementing the simulation cell (derived from the proposal's methodology and timeline):

1. **Multi-modal sensing pipeline** must support RGB-D, force/torque, and proprioception simultaneously at ≥50 Hz.
2. **Context buffer** must maintain K = 25–75 step history at 50 Hz across all modalities.
3. **Dual-layer safety** must be architecturally separable:
   - Contact-phase: admittance mediation on the policy output
   - Pre-contact: independent runtime filter on velocity/workspace/approach constraints
4. **Domain randomization** must be supported over: part tolerances, camera noise, initial misalignment, contact conditions, compliance parameters.
5. **ROS 2** is the orchestration layer — all components must expose ROS 2 interfaces for logging, monitoring, and intervention.
6. **PyTorch** is the ML framework — the context encoder and policy run in PyTorch, bridged to ROS 2.
7. **Reproducibility**: Metric logging (Safe Success, peak wrench, violations, interventions) must be systematic and exportable to CSV/JSON.
8. **Transfer gates** must be evaluable in simulation: ≥90% Safe Success + zero violations + bounded wrench.
9. **Ablation support**: Must be able to disable context inference, drop sensor modalities, and remove safety layers independently.
10. **Gazebo ↔ Isaac Sim uncertainty**: If Gazebo is the final platform, verify it supports the required contact physics, randomization, and F/T sensing fidelity. If Isaac Sim is required, plan migration.

## 12. What the Current Simulation Must Demonstrate First

Based on the proposal timeline (Months 1–6: Foundations; Months 4–12: Simulation + representation):

1. **Integrated robotic cell in simulation**: Robot, gripper, camera, peg, hole fixture all present with correct poses and TF frames.
2. **Baseline compliant control**: Joint trajectory execution verified (position control).
3. **Contact sensing pipeline**: Contact topics publishing with readable force vectors.
4. **Multi-modal observation logging**: RGB-D images, joint states, F/T data logged synchronously.
5. **Metric extraction**: Contact metrics node publishing insertion metrics.
6. **Safe task sequence execution**: Guarded pre-contact approach + contact detection + retreat cycle.
7. **Reproducible launch**: A single launch command that sets up the full cell and runs a validation sequence.

**Status:** Current workspace has validated v2.0–v2.16 sprints covering items 1–6. The workspace is ahead of the proposal's Month 6 foundations phase.
